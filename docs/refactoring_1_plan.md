# `ai-stack` refactoring plan

## Goal and baseline

Make the existing single-user, LAN-oriented voice assistant reliable and safe to publish, then establish small extension points for memory, tools, personas and additional clients. This is a plan only; none of the changes below are implemented here.

Current tracked application code consists of `compose.yaml` and the `py-server` voice pipeline. `llama-server` serves the Stheno GGUF model; PostgreSQL/pgvector is provisioned but not used by the Python code. Ollama and 9router are commented-out Compose examples, not active services. The Qwen coding model, wake word, memory, tool access, coding agent and additional clients are future work. Preserve the working single-user voice/text-to-STT-to-LLM-to-TTS flow while refactoring it.

## Prioritized work

### P0 — Protect public source and restore reproducible startup

1. **Audit and isolate local/private data.** Keep `.env`, TLS private keys/certificates, `db/data`, `router/data` (including tokens, SQLite state and machine identifiers), `ollama/data` (including keys), `models`, audio/transcripts, downloaded voices, CUDA libraries and caches out of Git and Docker build contexts. Verify both `git ls-files` and an ignored/untracked-file review before publishing; inspect *history* for previously committed secrets as a separate check. If real credentials or keys were ever published, rotate them and handle history deliberately rather than assuming `.gitignore` fixes past commits. Do not commit or print secret contents in diagnostics. Current Git-tracked files do not include the local `.env` or PEM files, but `py-server/.dockerignore` does **not** exclude `*.pem` or `certs/`: `COPY . .` in `py-server/Dockerfile` can embed local TLS material in images. Exclude those files from image builds and supply certificates explicitly at runtime only when TLS is enabled.
2. **Make examples safe and accurate.** Replace realistic-looking `.env.example` passwords/token prefixes with unmistakable placeholders and document which variables are actually consumed. The present `INITIAL_PASSWORD`, `HF_TOKEN` and `OPENAI_API_KEY` entries have no demonstrated use in the active pipeline; do not imply they are required. Avoid recording LAN IPs, user-specific hostnames, credentials, audio or transcripts in committed configs/docs. `.gitignore` currently uses broad `*.txt` and `*.pem` rules; prefer explicit runtime paths, preserving intentional tracked source/config examples.
3. **Fix dependency/installability baseline.** Convert `py-server/requirements.txt` from UTF-16LE to UTF-8 and verify `pip install -r py-server/requirements.txt` in a clean environment/image. Pin or constrain compatible Python packages and image versions, including GPU/runtime compatibility where relevant. Check whether `python-dotenv` is needed (`llm.py` imports `dotenv` but it is absent from requirements); remove the import if Compose is the source of configuration, or declare the dependency. Ensure Piper voice files and CUDA libraries are provisioned as documented runtime assets: `.dockerignore` excludes `voices/`, while `tts.py` loads `./voices/hal.onnx` and Compose bind-mounts the whole source tree. Build/start should not silently depend on files that happen to exist on one developer machine.

### P1 — Correct the current request and deployment path

4. **Use one supported container network/TLS configuration.** `compose.yaml` sets `LLM_API_URL=http://llama-server:8000/v1`, but `py-server/llm.py` ignores it and calls `http://host.docker.internal:8300/v1`. Read the configured URL, default to the Compose service DNS name, and separate internal HTTP from client-facing TLS. `py-server/Dockerfile` hardcodes a LAN-IP certificate and `--reload`; the browser HTML in `main.py` always opens `wss://`, even when a plain HTTP endpoint is used. Choose/document the TLS termination boundary and derive `ws://` versus `wss://` from the page protocol. Do not rely on a specific LAN IP or Docker Desktop host alias. Expose only ports actually needed by a LAN client; restrict DB/model ports to the internal network or loopback where feasible, and define the intended access boundary for the user-facing endpoint.
5. **Define the WebSocket contract and handle failure explicitly.** `main.py` currently accepts text or arbitrary bytes, has no message-size/duration limit, no end-of-turn or typed error frame, catches all exceptions (including disconnects) and prints them, and serializes blocking STT/LLM/TTS inside an async handler. Specify input/audio formats, request IDs/turn boundaries, text/status/error/audio events, disconnect and cancellation behavior, and bounded work/queues or backpressure. Offload or isolate blocking operations so one request cannot starve other connections; limit concurrent GPU workloads appropriate to the single-user machine. Add a minimal origin/access check suitable for the chosen LAN deployment boundary; do not treat a WebSocket connection as proof of authorization. Preserve ordered streaming WAV playback, and make the browser display errors/transcripts rather than silently ignoring text frames. Stop audio tracks and release object URLs/queued audio on failure or disconnect.
6. **Eliminate shared mutable scratch files.** `main.py` writes every incoming recording to `voice.webm`; `stt.py` writes `transcribed_text.txt`; `tts.py` uses `test.wav` for every chunk and loads the voice for each chunk. Two requests can overwrite each other's data, and personal audio/text persists on disk. Pass bytes/streams or use per-request temporary files with guaranteed cleanup; load/reuse the Piper voice at an appropriate lifecycle boundary, with concurrency control if needed. Return a typed success/error result for empty or failed transcription/synthesis instead of passing `None` to `send_bytes`. Avoid logging or persisting raw user content by default.
7. **Correct text-to-speech chunking.** `text_chunker.py` flushes the *whole* buffer as soon as any `.`, `!` or `?` appears after 15 characters, so punctuation in abbreviations/decimals and early punctuation inside a long stream can produce awkward speech; the final cleaned chunk may be empty; the regex `\*.*?\*` can remove unintended content across chunks. Define a bounded sentence/latency policy, handle empty deltas/finish events and post-cleaning empties, and test punctuation split across stream tokens and long unpunctuated output. Avoid treating formatting removal as a substitute for a documented speech rendering policy.

### P2 — Make components replaceable without premature infrastructure

8. **Separate transport, orchestration and providers.** Move the embedded HTML/JS out of `main.py`; keep FastAPI/WebSocket concerns at the edge and create an assistant turn coordinator with narrow STT, chat-stream, TTS and (later) conversation-store interfaces. Inject/configure adapters for faster-whisper, the OpenAI-compatible llama.cpp endpoint and Piper; keep provider-specific sampling parameters in the LLM adapter, rather than in the coordinator. Start with one supported implementation each and simple Python types; avoid a plugin framework until a second implementation exists. Centralize validated settings for model ID, prompt/persona, URLs, audio/voice paths, TLS mode and timeouts. The current `llm.py` hardcodes a character prompt, model name and sampling parameters, which prevents the assistant/coding use case from selecting an appropriate profile.
9. **Introduce persistence only with an explicit ownership model.** PostgreSQL is deployed but unused and `DATABASE_URL` is not consumed. Decide whether to keep it provisioned for the next milestone or make it optional until a store exists. For memory, design conversation/session/message identifiers, ordering, retention/deletion and migration strategy; keep transcript storage opt-in/intentional for a personal assistant. Start with a small store interface and schema migration workflow, then implement short-term history and cross-session recall with bounded prompt context. Keep long-term knowledge accumulation and vector retrieval as later decisions, not assumed consequences of having pgvector installed. Use a named volume or documented private path plus backup/restore guidance for DB state.
10. **Prepare scoped next-stage capabilities.** Define a persona/profile configuration and selection rules (default assistant vs fictional character vs coding) before adding wake-word switches. Keep wake-word detection at the audio/client boundary with an explicit activation state and fallback to existing push-to-talk. Introduce a small tool registry with explicit input/output schemas, execution timeout and an initial read-only tool; keep tool execution distinct from generated text and memory. Treat coding-agent workspace/file/command access as a separate capability boundary, with explicit working-directory limits. Keep router/Telegram/desktop/mobile/web provider integrations behind transport/LLM adapter contracts until implemented; remove or move stale commented-out Compose services to an examples/decisions document rather than presenting them as running services.

### P3 — Conventions, documentation and validation

11. **Apply consistent Python/client conventions.** Add formatting/linting/type-checking with a small documented config; use descriptive names (`response_stream` rather than `responseStream` in Python), typed public functions, structured logger instead of `print`, predictable import/order/indentation, and remove dead commented-out handlers and profanity in executable examples. Keep JS and Python style independently consistent. Prefer a small package layout such as `api`, `pipeline`, `providers`, `config` and `web` only where file growth warrants it.
12. **Replace `README.md` with a usable entry point.** The current file is an aspirational tree that lists absent `9router/`, `mcp/`, `storage/` and `prompts/` paths rather than installation instructions. Document actual vs planned components; architecture/data flow and trust boundaries; CPU/GPU/driver, model, voice and TLS prerequisites; how to create `.env` from the sanitized example; how to build/start/stop with Compose and connect to the browser/LAN client; what is stored locally; and basic troubleshooting. Add `docs/decisions/` for short architecture decision records (network/TLS, storage/memory, provider contracts) and `docs/issues.md` or an equivalent backlog for known limitations, owners/priority and follow-ups. Keep model/license/download details and performance/hardware assumptions explicit without committing large assets or private paths.
13. **Add meaningful verification at the changed boundaries.** Exercise startup with a clean checkout plus documented external assets; validate Compose config; test a text turn and an audio turn end-to-end with the real services on the target hardware. Add focused tests for chunking edge cases, configuration errors, WebSocket protocol/disconnects, scratch-file isolation/cleanup and provider substitution with fakes; add an integration smoke check for DB-backed sessions when persistence exists. Run formatting/lint checks, dependency/image build and secret/tracked-file scans before publishing. Do not require GPU downloads for fast unit checks.

## Suggested execution order and exit criteria

| Milestone | Deliverable | Evidence of completion |
| --- | --- | --- |
| 1. Safe baseline | P0 items 1–3 | No local keys/state in tracked files or image context; fresh install/build and documented asset setup succeed. |
| 2. Reliable voice path | P1 items 4–7 | LAN text and recorded-audio requests complete; errors/disconnects are visible; simultaneous turns do not mix audio/text or leave scratch artifacts. |
| 3. Stable boundaries | P2 items 8–9 | Transport depends on small interfaces; model endpoint/profile can be configured; session storage is intentional and migratable if enabled. |
| 4. Feature readiness | P2 item 10, P3 items 11–13 | Wake-word/tool/coding milestones have explicit contracts; README matches the running deployment; targeted checks and decisions are documented. |

Keep milestones 1–2 centered on the existing pipeline. Gate new features on their own acceptance tests instead of treating planned components as already operational.
